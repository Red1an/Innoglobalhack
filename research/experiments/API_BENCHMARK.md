## Ноутбук локально

1. Запустите Jupyter из клона репозитория и откройте `api_colab.ipynb`.
2. Выполните ячейки сверху вниз. Они создадут отдельное окружение CPU-клиента
   с зависимостями из `requirements-api.txt` внутри игнорируемого каталога результатов.
3. Текущая группа `baseline-dev-target093-v4` выбирает только `qwen3-235b-instruct`.
   GigaChat Pro уже прошёл139 строк с micro-F1=0.9360; его повторный запуск не нужен.
4. Введите ключ Caila в скрытом поле `getpass`. Для ClearML используются
   существующий `~/clearml.conf`, `CLEARML_CONFIG_FILE` или переменные окружения;
   если настройки отсутствуют, появятся скрытые поля для личных credentials.
5. Выполните проверку доступа и dry-run, затем ячейку прогона выбранных моделей.

`LIMIT=None` означает полный тест. `LIMIT=10` — отдельная проверка доступности,
формата ответа и задержки; для неё укажите другую `RUN_GROUP`, например `smoke-v1`.
Ключи в файлы ноутбука и результаты не записываются. Изменение параметров,
промпта, входных данных или версии кода требует новой группы/каталога.

## Две версии теста

Текущий ноутбук использует только утверждённый `data/test/test_gold.parquet` — 139 строк.
`DIRTY_TEST=None` исключает грязный набор: 6 моделей × 139 строк = 834 запроса.
Train в этот прогон не входит. Для отдельного сравнения с исходным грязным test
можно явно задать `DIRTY_TEST="data/raw/public-test-dataset.parquet"` (208 строк).
Для каждого набора будут отдельные задачи и строки лидерборда.
Изменение состава/разметки теста меняет измеритель качества; разница результатов
не означает эффект очистки train. Train в этих API-прогонах вообще не используется.

Поддерживаются JSONL/Parquet с `description`, `mcId`, `labels`, а также исходные
`categories`, `found_microcategories` и `y_102`…`y_106`.
Для исходных файлов без mcId явно принято 101. `labels=[]` — проверенное отсутствие
дополнительных услуг, а не отсутствие завершённой разметки.

## Ранний отсев моделей

Текущий бюджетный экран требует micro-F1≥0.93 на фиксированных первых30 строках.
Если экран не пройден, модель останавливается с причиной `budget_screen_f1`.
Это эвристика экономии: модель могла бы улучшиться на остатке, поэтому частичный
результат не считается доказательством низкого качества полного test.
После прохождения экрана модель пропускается, если итоговый micro-F1 уже
не сможет достичь 0.93 даже при идеальных ответах на все
оставшиеся объявления. Для верхней границы фиксируются уже полученные TP/FP/FN,
а все оставшиеся положительные метки добавляются к TP без новых ошибок.
Эталон используется только контроллером оценки и не передаётся модели.
Математическая граница отдельно гарантирует, что цель уже недостижима; бюджетный экран имеет другую причину остановки.

Параметры: `EARLY_STOP_MIN_ROWS=30`, `TARGET_F1=0.93`, `SCREEN_F1=0.93`;
CLI: `--early-stop-min-rows`, `--target-f1`, `--screen-f1`.
`--screen-f1` необязателен в CLI. В текущем notebook EARLY_STOP_MIN_ROWS=0: отсев целиком выключен для полного замера.
Значение `--early-stop-min-rows 0` отключает отсев.
Модель не перезапрашивается после остановки при повторе того же запуска.
Изменение порогов требует новой группы.
Доля невалидных ответов служит диагностикой и сама по себе не останавливает модель.
Старый `--max-invalid-rate` принимается с предупреждением для совместимости
с запущенными ранее клиентами, но больше не влияет на остановку.

В `evaluation.json` сохраняются статус, число обработанных/плановых строк,
хеш полного test и обработанного префикса, правило и причина остановки.
Для частичного теста ClearML использует имя `early-stopped`, теги
`early-stopped`/`screening-only` и метрики `screening/*`; обычный `micro_f1`
не публикуется. Частичный F1 нельзя ранжировать рядом с результатами полного test.
Полный входной test сохраняется для воспроизводимости, таблица предсказаний
содержит только реально обработанные строки. Сетевой сбой не считается отсевом.

## Контракт ответа и Pydantic

В `response_contract.py` используется Pydantic 2.11.5: `labels` обязателен,
ID должны быть строгими целыми 101–106, лишние поля запрещены. Строки, bool,
дробные числа и неизвестные ID отклоняются. `{}` остаётся ошибкой схемы;
из него не делается вывод о корректном отсутствии категорий.

Перед валидацией снимается только одна полная Markdown-обёртка. После проверки
ID удаляются исходная категория и повторы; каждое преобразование записывается
в `format_issues`. Если адаптер не передал `finish_reason`, завершённый JSON
с правильной схемой принимается с предупреждением. Явный `length`, фильтрация,
refusal или незавершённый/неразбираемый JSON отклоняются.

В `predictions.jsonl` сохраняются raw, нормализованные labels/valid,
исходные strict_labels/strict_valid, parse_error, format_issues и версия контракта.
Основной F1 считается после этих преобразований, `legacy_strict_micro_f1` и
`legacy_strict_invalid_rate` сохраняют оценку прежнего парсера (legacy/strict); это не строгость новой Pydantic-схемы. Прямое сравнение с прежним
строгим протоколом требует строгой метрики; итоговый F1 полного test не заменяется
частичным F1. Схема JSON и снимок валидатора выгружаются в ClearML.

Pydantic проверяет ответ в Python. Принудительная генерация по `response_format`
не включается: [совместимый API Caila](https://docs.caila.io/hub/api/openai-api/)
не гарантирует одинаковую поддержку JSON Schema у всех выбранных провайдеров.
Системный промпт из dev остаётся неизменным.

`REUSE_RUN_GROUP="baseline-dev-schema-v3"` в ноутбуке берёт уже оплаченные ответы
из прежней группы и перепроверяет новым валидатором. `--reuse-from` в CLI указывает
на предыдущий каталог вывода конкретной модели. Должны точно совпасть модель,
параметры, промпт, base URL, полный набор строк и хеши предсказанных строк.
Продолжение запрашивает только оставшиеся объявления; `reuse.json` фиксирует
происхождение и число переиспользованных ответов. Изменённые промпты или данные
не допускают такой перенос. Старые результаты не переписываются.

## ClearML

Проект по умолчанию — `avito-microcategories`. Каждый завершённый прогон
«модель × версия test» автоматически выгружается отдельной задачей.
Перед расходованием токенов выполняется read-only проверка подключения,
без создания проверочных задач в лидерборде.

Сохраняются micro-F1, precision/recall, exact match, F1 каждой категории,
invalid rate, p50/p95 задержки, число токенов и повторных запросов.
Артефакты: run.json с параметрами/версиями/системным текстом, manifest.json,
test.jsonl, predictions.jsonl с исходными ответами и usage, errors.jsonl,
metrics.json, prompt.txt, drafts.json, model_catalog.json, evaluation.json,
response_contract.py, response_schema.json, reuse.json (если был перенос), снимки кода и ноутбука.
В таблице видны эталоны и предсказания, при INCLUDE_DATASET=True также тексты.
Метрики API не оценивают качество сгенерированных объявлений: title/text равны null.

После успешной синхронной выгрузки сохраняется `clearml.json` с ID и ссылкой.
Повтор той же выгрузки не создаёт дубликат. Если загрузка сорвалась, используйте
`export_model(name)` в ноутбуке или CLI `--export-only`: повторных Caila-вызовов не будет.
Если задачу удалили на сервере, явная повторная выгрузка доступна с `--force-upload`.
При сетевом сбое частичные предсказания остаются локально; задача с окончательными
метриками создаётся только после завершения пары модель/тест.

Задержка включает сеть и backoff. Стоимость не вычисляется из чужих тарифов:
usage сохраняется полностью, фактическую сумму проверяйте в аналитике Caila.
Текущие цены опубликованы в [API прайса Caila](https://caila.io/api/mlpcore/pricing).
Произвольное сопоставление сокращённых ценовых ID с полными model ID недопустимо.

## CLI

Используйте Python из окружения ноутбука или установите `requirements-api.txt`.
Ключ должен быть в `CAILA_API_KEY`; адрес доверенного HTTP(S)-прокси при необходимости
можно передать через `CAILA_PROXY`. `--direct` отключает только HTTP-прокси процесса,
но не VPN-туннель. SOCKS-прокси этот скрипт не поддерживает.

```powershell
python research/experiments/api_bench.py --dry-run
python research/experiments/api_bench.py --out research/api-runs/ru-cn-baseline-v1

# Текущий baseline: только утверждённый чистый test, без грязного набора и train:
python research/experiments/api_bench.py --skip-dirty --clean data/test/test_gold.parquet --out research/api-runs/ru-cn-gold-v1

# Повторить только сохранение готовых результатов в ClearML:
python research/experiments/api_bench.py --export-only --out research/api-runs/ru-cn-baseline-v1
```

В Colab загрузите комплект zip через первую ячейку: он содержит снимок кода,
этот ноутбук, конфигурацию моделей, утверждённый чистый и исходный грязный test. Результаты можно
сохранять на Drive; credentials ClearML потребуется ввести отдельно.
Комплект собран в `research/api-runs/delivery/caila-baseline-bundle.zip`.
После изменения кода обновите его командой
`python research/experiments/build_api_bundle.py` — сборщик использует явный
список файлов и не включает ключи, конфигурацию ClearML или результаты прогонов.
Прохождение `--dry-run` не проверяет доступ ключа к модели или биллинг.

Невалидный ответ считается пустым предсказанием и отдельно учитывается в invalid rate.
HTTP-сбой после повторов прекращает текущий прогон; он не превращается в отрицательную
метку. При таймауте запрос мог быть обработан сервером и повтор может списать токены снова.
Не запускайте два процесса в один каталог результатов одновременно.
