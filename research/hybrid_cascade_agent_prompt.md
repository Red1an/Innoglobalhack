### 3. Архитектура, которую нужно реализовать (пакет/модули, например `src/hybrid_cascade/` или `research/hybrid_cascade/`)

#### Шаг А. Препроцессинг входа (без потери исходного текста)
- Принимает `{ "description": str, "mcId": int, ... }`.
- Для **Stage 1** строит нормализованный текст `norm_text`:
  - `unicodedata.normalize("NFC", ...)` + нормализация пробелов;
  - замена латинских омоглифов внутри кириллических слов (`HOMOGLYPHS` из `scripts/hard/dynamic_prompt.py`);
  - разделение склеек цифр/эмодзи/регистра (`keycap_spacing`, `joined_list` из `dataset_review/train_text_cleaning.py`), чтобы не проваливаться на срезе `dirty_text_and_homoglyphs`.
- **Stage 2 (LLM)** получает читаемый текст (с сохранённой структурой абзацев/хвостов, при желании после мягкой де-омоглифизации).
- Обязательно поддерживай **любой входной `mcId` in `{101..106}`**, в конце всегда исключай `mcId` из предсказанного списка (если `mcId != 101`, не падай с ошибкой `supports source 101 only`).

#### Шаг Б. Stage 1 — Обученный классификатор с вероятностями `p_102..p_106`
Сделай единый интерфейс Stage-1 провайдера (возвращает словарь вероятностей `{102: float, ..., 106: float}` и поклассовые пороги с `dev`):
1. **CPU-бэкенд (`char-lr` / `char+word-lr`):** обученный на `train_fit` `TfidfVectorizer` + `OneVsRestClassifier(LogisticRegression)` строго по **5 целевым столбцам `102–106`** через `.predict_proba()` (без 6-го константного столбца `101`, чтобы не словить старый баг порога `0.6225`!). Проверь также объединение `char_wb (3,4)` + `word (1,2)` TF-IDF — замерь на `dev`, даёт ли оно прирост против чистого `char-lr`.
2. **Нейросетевой бэкенд (`rumodernbert` / `giga-embeddings` / загрузка сохранённых `scores`):** если есть обученный чекпоинт `RuModernBERT` (из `bench.py`) или кэш `predictions.jsonl` с полем `scores`, уметь брать `p_102..p_106` из него (и поддерживать блендинг `w * p_bert + (1 - w) * p_lr`).
3. Подбери на `dev` как общий порог `t_global`, так и (опционально) поклассовые `t_class[102..106]` с проверкой на переобучение.

#### Шаг В. Router — Логика принятия решения (Freeze vs Escalate)
Для каждого объявления анализируются `p = {102..106}` и сработавшие детекторы в `norm_text`:
1. **Заморозка `0` (Confident Negative):** если `p[k] < t_low` (например `0.15–0.22`) И не сработал спасательный редкий триггер → ставим `0` и **запрещаем LLM трогать эту категорию** (убирает галлюцинации LLM).
2. **Заморозка `1` (Confident Positive):** если `p[k] > t_high` (например `0.75–0.85`) И для категории `k` не сработал ни один контекстный триггер-ловушка → ставим `1` без вызова LLM.
3. **Эскалация в Stage 2 (`uncertain`):** категория `k` попадает в список спорных, если:
   - `t_low <= p[k] <= t_high` (серая зона неуверенности классификатора), **ИЛИ**
   - `p[k] >= t_trap` (например `>= 0.20`) И сработал **триггер контекстной ловушки** по правилам `guide_v2_rules.md`:
     - *Глобальные ловушки:* отрицания (`не`, `нет`, `без`, `кроме`, `вместо`, `исключая`), чужая работа / неисполнитель (`заказчик`, `смежник`, `партнер` без сметы, `рекоменд`, `застройщик`, `знакомый`), не-услуги (`технадзор`, `приемк`, `тепловизор`, `дизайн-проект`, `проектирован`, `чертеж`, `ваканси`, `требуются в бригаду`, `продажа`, `доставка`, `только демонтаж`).
     - *Ловушки `102`:* `выравниван` или `шпакл/шпатл` без `штукатур/маяк`; «штукатурка под обои/покраску» (не должна сама давать `106`, если шпаклёвки нет).
     - *Ловушки `103`:* `пвх-плит`, `кварцвинил`, `ламинат`, `линолеум`, `отмыв/уборка` плитки.
     - *Ловушки `104`:* `тепл* пол` (нужен тип: водяной=104, электрический=105, не указан=0), `подключен` техники (к воде/сливу=104), `гидроизоляц`.
     - *Ловушки `105`:* `тепл* пол`, `подключен` техники (варочная/духовка=105), `план/проектирование розеток`, `штроблен`.
     - *Ловушки `106` (строго по `guide_v2_rules.md`!):* `шпакл/шпатл`, `грунт`, `шлифов`, `стеклохолст`, `стык/шв гкл/гипсокартон` (только швы ГКЛ ≠ 106, вся поверхность под отделку = 106), `под покраск / под обои`, `снятие/демонтаж старых обоев`, `реставрация ванн`, `венецианск/декоративн штукатурк`.
4. **Спец-правило для `mcId != 101` (компенсация отсутствия `101` в train):**
   - Т.к. в `train_guide_v2` нет примеров предсказания `101`, если входной `mcId != 101`, автоматически добавляй `101` в `uncertain` при наличии комплексных маркеров (`под ключ`, `капитальн`, `косметическ`, `полный цикл`, `санузел под ключ`, либо если Stage 1 уверен сразу в ≥2 категориях) — Stage 2 LLM проверит, является ли объявление комплексным ремонтом `101`.
5. **Переключатель SEO-политики (`--seo-mode off|on`):**
   - Поддержи два режима для стратегии 2–3 попыток на привате: `off` (теги в конце не считаются, как в `test_guide_v2`) и `on` (услуги в хэштегах/ключевых словах в конце учитываются). Если категория сработала только из-за ключевых слов в хвосте — маршрутизируй в Stage 2 с соответствующей строкой правила `S3`.

#### Шаг Г. Stage 2 — LLM-арбитр с модульным динамическим промптом и кэшем
- Если `uncertain` пуст (~75–80% объявлений) — LLM **не вызывается вообще** (время ~1–20 мс, стоимость 0 ₽).
- Если `uncertain` не пуст:
  - Собирается **короткий динамический промпт**:
    1. Краткое ядро роли + описание ТОЛЬКО категорий из `uncertain` (и при желании список уже замороженных категорий как контекст, чтобы LLM не тратила внимание).
    2. Точечные правила из `guide_v2_rules.md` только для сработавших триггеров (например, если сработала ловушка `теплый пол` или `шпаклевка/ГКЛ`, вставляем ровно этот микро-блок с 2 примерами «ставить / не ставить»).
    3. Жёсткий JSON-контракт ответа только по спорным ID: `{"decisions": {"102": true, "106": false}}` (или `{"labels": [...]}` с маской заморозки в пост-процессинге, чтобы LLM физически не могла поменять замороженные `0` и `1`!).
  - Поддержи два транспорта:
    - **Local Ollama** (`avibe-q8`, `t-lite-q8`, `qwen3:4b-instruct` и др., JSON schema в `format`, `temperature=0`, `seed=42`).
    - **Caila / OpenAI-compatible API** (переиспользовать `api_bench.py` и модели из `api_models.json`, например `qwen3-235b-instruct` / `deepseek-v3.1-chat` / `qwen3-30b`).
  - **Обязательный дисковый кэш LLM-ответов** (SQLite или JSONL по ключу `(sha256(text), model_id, sha256(system_prompt), sorted(uncertain))`), чтобы при подборе порогов роутера или повторных прогонах не платить дважды и не ждать.
  - **Fallback:** при таймауте/ошибке LLM безопасно возвращается решение Stage 1 с порогом `dev`.

4. После всех прогонов занеси результаты, метрики и стоимость в свой лог в `decisions/`.
